KaruFile 画像圧縮の内部仕様

この文書は、media-shrink-tool コンポーネントが画像をどう圧縮・変換するかを、 実装に基づいて詳しくまとめたものです。 エンドユーザー向けの手順は MANUAL.md、 保存先や status の一覧は REFERENCE.md、 個別 CLI の簡潔な説明は media-shrink-tool/README.md を参照してください。

1. 概要

KaruFile の画像処理は、入力画像を一切変更・削除せず、別の出力ツリーへ変換済み JPEG を書き出すことを目的としています。 処理は以下の原則に基づきます。

  • 入力ファイルを書き換えない。出力は別ディレクトリ。
  • 入力と出力が同一・親子関係になる指定は、実行前に拒否する。
  • symlink / junction / hard link 等の危険なリンクを検出して拒否する。
  • 縦横比を維持し、拡大・切り抜きは行わない。
  • EXIF Orientation は画素へ適用し、出力から Orientation タグは削除する。
  • アルファ通道は白背景に合成する。
  • JPEG への保存時に「いつ・どのレシピで生成したか」を marker として埋め込み、再実行時の再利用を可能にする。
  • 1ファイルの失敗で他のファイルの処理は止めない。

2. 対応形式

探索対象となる拡張子は以下の通りです。大文字小文字は区別しません。

.jpg .jpeg .png .tif .tiff .bmp .gif .webp .heic .heif

HEIF/HEIC は pillow-heif が利用可能な場合のみ対応します。DLL 未インストール等で初期化に失敗しても、対応拡張子の列挙自体は続行し、実ファイル処理時に失敗します。

出力形式は常に JPEG です。拡張子の扱いは次の通りです。

入力出力パス例
photo.jpgphoto.jpg
photo.jpegphoto.jpeg
photo.pngphoto.png.jpg

3. 変換プリセット

画像レシピは media-shrink-tool/src/media_shrink/config.py に定義されています。現在は standard と compact の 2 つです。

項目standardcompact
長辺上限1280 px1024 px
短辺上限960 px768 px
JPEG quality7260
サブサンプリング4:2:04:2:0
optimizetruetrue
progressivetruetrue
アルファ処理白背景合成白背景合成
Orientation画素適用画素適用

レシピ hash は以下の文字列です。これが marker に埋め込まれ、同一レシピ判定に使われます。

  • standard: 2f60924f29b4cedccd15bd92d6dab4da72b22c1358c23e2edf1174fa3b70f420
  • compact: c5233dcedea2119fbfa723eb7020ba4f295d0fbcb0881ec8340f389614a26ddd

hash は max_long=<N>, max_short=<N>, quality=<N>, subsampling=4:2:0, alpha=white, orientation=apply を改行で連結した SHA-256 です。設定値が変われば hash も変わり、旧 marker は自動的に「未知のレシピ」として再処理されます。

4. 出力寸法の計算

寸法計算は calculate_output_size() で行います。Orientation 適用後の寸法を前提に、次式でスケールを決めます。

scale = min(1.0, max_long / long_side, max_short / short_side)
new_w = max(1, round(width  * scale))
new_h = max(1, round(height * scale))

つまり、上限内に収まり、かつ縦横比を維持する最大寸法を選びます。scale=1.0 の場合は元の寸法のままです。

計算例（standard）:

元寸法出力寸法備考
(4032, 3024)(1280, 960)長辺を 1280 に収める
(3024, 4032)(960, 1280)縦長を 1280 に収める
(3000, 3000)(960, 960)短辺上限も考慮
(4000, 300)(1280, 96)極端な比率でも短辺上限内
(640, 480)(640, 480)アップスケールしない

5. 入出力の安全性検査

すべての入出力操作の前に、media-shrink-tool/src/media_shrink/utils.py の検査関数を通します。

5.1 入力ディレクトリの検査

  • 入力は解決可能なディレクトリであること。
  • 入力ルートからソースファイルまでに symlink / junction / reparse point がないこと。
  • ソースファイル自身が symlink でないこと。
  • 解決済みパスが入力ルート外に出ないこと。

5.2 出力ディレクトリの検査

  • 出力ディレクトリが入力ディレクトリと同一でないこと（Windows では大文字小文字無視）。
  • 出力ディレクトリが入力ディレクトリの内部でないこと。
  • 入力ディレクトリが出力ディレクトリの内部でないこと。
  • 出力先までのパスに symlink / junction / reparse point がないこと。
  • 出力先が既存のリンク、ディレクトリ、hard link ではないこと。
  • 既存の出力ファイルが入力ファイルと同一 inode を指していないこと。

5.3 補助ファイルの検査

レポートや manifest などの「sibling」ファイルも、入力領域と重ならず、既存ディレクトリ・リンク・hard link にならないことを検査します。

6. ファイル収集と出力計画

6.1 collect_images

collect_images() は、入力ディレクトリを再帰的に走査し、対応拡張子の通常ファイルを列挙します。

  • os.scandir() を使い、リンクは follow_symlinks=False で見ません。
  • symlink / junction / reparse point を含む入力パスは即座に PathValidationError として拒否します。
  • ファイルは相対パス（大文字小文字無視）→ 元の相対パスでソートされます。

6.2 plan_outputs

変換前に、すべてのソースに対する出力パスを先に決めます。これにより、実行中の出力衝突を防ぎます。

  1. 非 JPEG 入力は <basename>.jpg を付加。
  2. JPEG 入力は元の拡張子を維持。
  3. 大文字小文字を無視して同名・同じディレクトリ prefix になる出力があれば、相対入力パスの SHA-256 先頭 8 文字をファイル名に追加して解消します。
  4. 8 桁 hash で解消できない重複が残った場合は OutputCollisionError で停止します。

例:

input/photo.png      -> output/photo~a1b2c3d4.jpg
input/photo.png.jpg  -> output/photo~e5f6789a.jpg
input/kept.jpeg      -> output/kept.jpeg

7. 1画像あたりの処理フロー

process_image() は 1 枚の画像を処理します。以下の順序で実行されます。

  1. 入力・出力パスの解決と安全性検査
  2. ソースファイルの stat と SHA-256 を取得（SourceFingerprint）
  3. Pillow で画像を開き、format / mode / 元寸法 / EXIF Orientation / フレーム数を調べる
  4. 既存 marker を解析。同じレシピ・同一ソースで生成済みなら「SKIPPED_GENERATED」短絡
  5. 既存の完成済み出力が現在のソース・レシピと一致すれば「SKIPPED_COMPLETE」または「SKIPPED_COPY」短絡
  6. EXIF Orientation を画素に適用（ImageOps.exif_transpose）
  7. 透過を白背景に合成、モードを RGB に変換
  8. 出力寸法を計算し、必要なら LANCZOS で縮小
  9. dry-run ならここで予定寸法を返す（DRY_RUN）
  10. 一時ファイルへ JPEG 保存（marker 付き）
  11. 一時ファイルを検証（寸法・marker）
  12. 候補サイズをもとに採用/原本コピーを決定
  13. 採用時は os.replace() で正式出力へ原子公開
  14. 結果 dict を返す

7.1 Orientation の扱い

Orientation タグ（EXIF ID 274）が 2〜8 の場合は、ImageOps.exif_transpose() で画素を回転・反転してから処理します。出力 JPEG には Orientation タグを残さず、元の向きで保存します。

7.2 透過処理

アルファ通道を含む画像（RGBA、またはパレット透過を持つ P）は、白背景 (255,255,255,255) に alpha_composite してから RGB 変換します。警告 ALPHA_FLATTENED が出力されます。

7.3 アニメーション・複数ページ

先頭フレームのみを使用します。失われたフレームに対して警告を出します。

元形式警告
GIF, WebP（アニメーション）ANIMATION_DROPPED
TIFF, MPO（複数ページ）MULTIPAGE_DROPPED

8. JPEGエンコード

JPEG 候補は Pillow の Image.save() で生成します。常に以下のパラメータを使用します。

  • quality: プリセット値（standard=72, compact=60）
  • subsampling=2: Pillow では 4:2:0 を意味します
  • optimize=True
  • progressive=True

8.1 メタデータの保持

_optional_metadata() は、Orientation 適用後の画像から以下のメタデータを可能な限り抽出します。

項目抽出元条件・注意
EXIForiented.getexif()Orientation タグ（ID 274）は削除
ICC プロファイルsource.info["icc_profile"]RGB/RGBA/RGBX/RGBa/P のときのみ保持
XMPinfo["xmp"]bytes または str のとき
DPIinfo["dpi"]正のタプルのとき

保持できなかった場合は EXIF_DROPPED / ICC_DROPPED / XMP_DROPPED / DPI_DROPPED 警告が出ます。

8.2 フォールバック保存

既存 JPEG comment が長すぎる、または Pillow に渡せないメタデータがある場合に備え、 _save_jpeg() は 4 通りの組み合わせを順に試行します。

  1. combined_comment + metadata
  2. marker only + metadata（既存 comment 廃棄 → COMMENT_DROPPED）
  3. combined_comment + no metadata（METADATA_DROPPED）
  4. marker only + no metadata（両方廃棄）

どの組み合わせでも保存できなければ、JPEG 入力であれば原本コピー、それ以外は ERROR になります。

8.3 候補検証

保存後、_verify_candidate() で一時ファイルを検証します。

  • 寸法が予定値と一致すること
  • 長辺・短辺がプリセット上限を超えていないこと
  • JPEG comment に karufile:image-v2 marker が含まれていること

9. 候補採用条件

JPEG 候補を採用するか、入力をそのままコピーするかは、以下の条件で決まります。

adopt_candidate = (
    not source_is_jpeg
    or must_resize
    or orientation_applied
    or (reprocess_generated and savings > 0)
    or (savings >= JPEG_MIN_SAVINGS and reduction >= JPEG_MIN_REDUCTION)
)

定数は JPEG_MIN_SAVINGS = 32 KiB、JPEG_MIN_REDUCTION = 10% です。

  • 非 JPEG 入力 → 必ず JPEG 変換を行います（元形式に戻せないため）。サイズが元より大きくなる場合は OUTPUT_LARGER_THAN_SOURCE 警告。
  • リサイズが必要 → 必ず採用。
  • Orientation 適用が必要 → 必ず採用。
  • compact へ再処理する生成済み standard 画像 → 候補が小さければ採用。
  • その他の JPEG → 32 KiB 以上かつ 10% 以上削減できなければ原本コピー。

10. 生成済み・完成済み画像の再利用

再実行時には、すでにある出力を再エンコードせずに再利用する経路が 3 つあります。

10.1 SKIPPED_GENERATED

入力 JPEG 自身が KaruFile 生成済みで、現在のレシピと完全に一致し、かつ Orientation 適用が不要・寸法上限内なら、 入力をそのまま出力へコピーします。未知・破損・旧 v1 marker は無視して通常判定へ戻ります。

10.2 SKIPPED_COMPLETE

前回の実行で完成した出力ファイルが、同一ソースの stat・SHA-256・レシピ hash を含む marker を持ち、 寸法が上限内なら、完成出力をそのまま利用します。

10.3 SKIPPED_COPY

standard プリセット時、JPEG 入力がリサイズ不要で「原本コピー」されていた出力が、バイト列まで同一なら再利用します。 compact では既存コピーを再評価するため SKIPPED_COPY にはなりません。

11. Markerの仕組み

KaruFile が生成した JPEG には、ソースの同一性とレシピを示す marker が JPEG comment として書き込まれます。 

karufile:image-v2;recipe=<sha256>;src_size=<bytes>;src_mtime_ns=<nanoseconds>;src_sha256=<sha256>

例:

karufile:image-v2;recipe=2f60924f29b4cedccd15bd92d6dab4da72b22c1358c23e2edf1174fa3b70f420;src_size=3842048;src_mtime_ns=1725849600000000000;src_sha256=aabbccdd...

marker は正規表現で解析されます。version、recipe hash、src_size、src_mtime_ns、src_sha256 が一致した場合に「同一ソース・同一レシピの生成済み」とみなします。v1 marker や sha256 の欠落は信頼できないため、通常の候補判定に戻します。

12. レポートとManifest

画像処理の結果は、出力ディレクトリと sibling に 2 種類の CSV で保存されます。

12.1 画像エラーレポート

<output>.image-errors.csv

列: source,planned_output,error

画像処理が起動し、レポート公開に成功した場合にのみ更新されます。検査・起動・公開に失敗すると終了コード 1 となり、以前の CSV が残ることがあります。

12.2 画像結果 manifest

<output>.image-manifest.csv
<output>.image-manifest.dry-run.csv

列:

source_path,source_size,source_sha256,output_path,output_size,output_sha256,
action,error,preset,recipe_hash,orig_width,orig_height,new_width,new_height

manifest 行は、処理時の snapshot を使って検証されます。write 前にもう一度全 source/output を照合し、 整合しない場合は失敗します。正式ファイルへの公開は一時ファイルを os.replace() で移動する原子操作です。

13. 並列実行

process_all() は、対象数・worker 数に応じて逐次または ThreadPoolExecutor で実行します。 並列数は --workers（既定 4）で制御します。 結果リストは入力順を維持するためにインデックスで配置されます。

15. 警告・エラー・終了コード

15.1 警告（ターミナル出力のみ）

警告は画像エラー CSV には保存されません。主な警告は以下の通りです。

警告発生条件
ANIMATION_DROPPEDGIF/WebP アニメーションの先頭フレームのみ使用
MULTIPAGE_DROPPEDTIFF/MPO の先頭ページのみ使用
ALPHA_FLATTENEDアルファ通道を白背景に合成
EXIF_DROPPEDEXIF を保存できなかった
ICC_DROPPEDICC プロファイルを保存できなかった
XMP_DROPPEDXMP を保存できなかった
DPI_DROPPEDDPI を保存できなかった
OUTPUT_LARGER_THAN_SOURCE非 JPEG 変換で出力が元より大きくなった
ENCODE_FAILED_ORIGINAL_COPIEDJPEG 再エンコード失敗、原本コピーで回復
COMMENT_DROPPED既存 JPEG comment を廃棄して保存
METADATA_DROPPEDメタデータを廃棄して保存

15.2 主な Action

Action意味
