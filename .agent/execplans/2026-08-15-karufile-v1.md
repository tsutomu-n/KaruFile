## Goal

Windows 上で、Repo ルートの `karufile.py` から PDF と画像を別出力フォルダーへ非破壊で一括軽量化でき、個別失敗を CSV と終了コードで検出できる KaruFile v1 を完成させる。

## Acceptance Criteria

- `uv run --script karufile.py --help` が成功する。
- 入出力が同一または親子関係なら processor 起動前に終了コード 1 で拒否する。
- 画像は EXIF Orientation 適用後、長辺 1280px・短辺 960px 以内の JPEG となり、原本を変更しない。
- 出力名衝突、二重 JPEG 圧縮、部分ファイル公開を防止する。
- 画像失敗は `<output>.image-errors.csv` と終了コード 1 へ反映する。
- PDF のスキャン判定は最大画像、可視 texttrace、実効 DPI を使い、既存処理契約を維持する。
- PDF、画像、orchestrator の各 suite、入口 smoke、compileall、`git diff --check` が成功する。

## Scope

### In Scope

- ルート入口、README、orchestrator の表示・検査・終了コード。

### Out of Scope

## Discoveries

- ZIP の marker 表記に大文字小文字の矛盾がある。
- パスの大文字小文字が実行環境で区別される。
- `uv run --project pdf-shrink pytest -q` は Windows trampoline の path canonicalize で起動前に失敗するが、同じ環境の `python -m pytest -q` は 24 件成功した。テスト本体の baseline 失敗ではない。
- media-shrink-tool には baseline 時点でテストがなく、CLI help と正しい project `src` の compileall は成功した。
- 出力root配下の既存Junctionが入力へ向く場合、画像/PDFの公開先が入力原本へ解決される経路をWindows実機で再現した。
- `Path.rglob()` はこのWindows環境で入力配下のJunctionを追跡するため、入力探索も明示的な非追跡走査が必要だった。
- 画像のplanned fileと別planned outputのディレクトリprefix、PDF/画像間のprefixにも事前衝突が必要だった。
- Windows read-only属性は `copy2()` で一時出力へ継承され、再実行時の `os.replace()` とcleanupを妨げる。
- PDFのSQLite状態DBは既存WAL sidecarが入力へのhardlinkだと入力bytesを変更し得るため、DB本体だけでなくjournal/WAL/SHMもpreflight対象にする必要がある。

## Decision Log

### Decision-001

- Date: 2026-08-15
- Decision: ユーザーの製品名変更差分を保持して作業を継続する。
- Rationale: 差分は今回の固定要件と一致し、対象ロジックとの衝突がない。
- Alternatives: 停止して確認する、差分を巻き戻す。
- Consequences: 同じ行を編集する際は現在内容を基準に patch する。

### Decision-002

- Date: 2026-08-15
- Decision: marker は lowercase `karufile:image-v1` で保存し、検出は case-insensitive にする。
- Rationale: 製品の機械可読 identifier と二重圧縮防止の双方を満たす。
- Alternatives: 資料の一方だけを字面どおり採用する。
- Consequences: 過去の表記揺れも安全側で skip できる。

### Decision-003

- Date: 2026-08-15
- Decision: 入力のsymlink/Junctionは追跡せずfail closedとし、planned output・state・reportをprocessor起動前とpublish直前に検査する。
- Rationale: 別出力指定だけでは、既存reparse pointやhardlinkを介した入力変更を防げないことを実機再現した。
- Alternatives: top-level入出力のresolve比較だけを維持する。
- Consequences: linkを含む入力や危険な既存出力は終了コード1で明示的に拒否する。

### Decision-004

- Date: 2026-08-15
- Decision: JPEG候補生成はOrientation・色変換・resizeを含めて復旧境界へ置き、失敗時は原JPEGを原子的にコピーする。必須変換を適用できなければerrorにする。
- Rationale: encode直前だけの例外処理では、候補準備失敗時に出力ミラーが欠落する。
- Alternatives: 全て単純errorとして出力を残さない。
- Consequences: 原本ミラーは維持しつつ、要件未達をCSVと終了コードで検出できる。
